# SteamHangar v0.1.0

SteamHangar is a self-hosted, Docker-first Steam LAN download cache with
per-game management: you see which game occupies how much space and delete
single games from the cache, and a scheduler prefills updates for the games
your PCs have installed. v0.1.0 is the first stable release; v0.1.x gets bug
fixes only. Supported setup:

- **Server stack** (Docker Compose): vault-core (nginx cache, ports 80 and
  443), vault-api (API, scheduler, web UI; the vault-runner service runs the
  same image), vault-dns (optional) and vault-proxy.
- **vault-agent** for gaming PCs: Windows (Scheduled Task) and Linux (systemd
  timer), reports installed games.
- **Android app** (signed APK) and the **web UI** served by vault-api.

The image digests, the agent `SHA256SUMS` and the APK digest of this exact
build are in the "Components" and "Verify this release" sections at the end
of this release.

## Before you upgrade or install

- **Back up the `vault-db` volume.** vault-api upgrades its schema at start;
  an older image refuses a newer database (by design), so a rollback needs
  the backup ([Upgrading](../../deploy/README.md#upgrading)).
- **Cache volume ownership (SEC-FIX-5).** Only `cache/depot` belongs to
  `101:101`; the cache root, `cache/`, `tmp/` and `logs/` belong to
  `root:root` (0755). vault-core migrates an older layout at its first start
  (one `(migrated)` log line per directory) and refuses to start, naming the
  host commands, when it cannot (no CAP_CHOWN, root-squashing NFS, userns
  remap). A **rollback to an image from before SEC-FIX-5 needs the old
  ownership back first** (untested commands in
  [Upgrading](../../deploy/README.md#upgrading)).
- **Bind mount (`VAULT_CACHE_PATH`).** It must be an absolute path, and
  `<path>/cache/depot` and `<path>/tmp` must exist before the first start,
  with `cache/depot` chowned to `101:101` and the rest left `root:root`
  ([Using a dedicated cache mount](../../deploy/README.md#using-a-dedicated-cache-mount)).
  A named volume (the default) needs nothing.
- **Dedicated `VAULT_CORE_BIND` needs `extra_hosts`.** If port 80 is taken
  on the host, give vault-core its own address (`VAULT_CORE_BIND=10.0.0.50`),
  never another port. Then SteamPrefill inside the stack may not find the
  cache on its own: pin `lancache.steamcontent.com` to that address with
  `extra_hosts` on `vault-runner` in a `compose.override.yaml` (a plain
  private IPv4 address, not a host name). Details: deploy/README.md "Fix it
  (only needed with a dedicated `VAULT_CORE_BIND`)".
- **Port 443.** The HTTPS passthrough (`VAULT_TLS_PASSTHROUGH`, on by
  default) is only published on the LAN when `VAULT_TLS_BIND` is set; set it
  to the address your DNS rewrite answers
  ([Port 443](../../deploy/README.md#port-443-the-https-passthrough)).
- **Blank no longer means off (since rc18).** For `VAULT_SCHEDULE_WINDOW`,
  `VAULT_UPSTREAM_EDGE`, `VAULT_UPSTREAM_RATE`, `VAULT_UPSTREAM_POOL_HOSTS`
  and `VAULT_UPSTREAM_RATE_WINDOW` a blank value means "not set" (Settings,
  else the default); write `off` where a blank used to switch something off.
- **Windows agent.** Existing installs keep the old Scheduled Task action
  (a console window flashing on every run) until `install-task.ps1` is run
  once more (AGENT-FIX-3). A re-install keeps the key and the client id.

## DS-Lite / CGNAT lines: upstream connection pooling

On a line whose IPv4 goes through the provider's carrier-grade NAT (DS-Lite
and similar), every new upstream connection uses a port mapping. A Steam
client downloading a game that is not cached used to open one connection
per chunk; the NAT's port quota ran out (`connect() failed (113: Host is
unreachable)`) and the whole household briefly lost new IPv4 connections.

Fixed in this release (CORE-FIX-4,
[ADR-0021](../adr/0021-one-pooled-upstream-and-global-connection-cap.md)),
on by default:

| Variable | Default | Meaning |
|---|---|---|
| `VAULT_UPSTREAM_EDGE` | `dist-fra1.discovery.steamserver.net` | Every cache MISS is fetched over pooled keepalive connections to this ONE edge, whatever host the client asked for. `off` = rollback to the older per-name pool, which **keeps the old CGNAT limitation**. A blank value means "not set" (Settings, else the default), not rollback. |
| `VAULT_UPSTREAM_MAX_CONNS` | `16` | Global cap on concurrent upstream connections, 1..64, no off switch. Above it vault-core answers **503** at once and the client retries. Must be at least `VAULT_PREFILL_MAX_THREADS` or vault-core refuses to boot. |
| `VAULT_PREFILL_MAX_THREADS` | `8` | Chunk requests one prefill keeps in flight (1..64); also the floor for the cap above. |
| `VAULT_TLS_CLIENT_MAX_CONNS` / `VAULT_TLS_MAX_CONNS` | `64` / `256` | Caps of the HTTPS passthrough per client address (1..256) and in total (1..400). A client over the per-client cap retries refused connections at once, which a gateway may log as a SYN flood; count the `status=503` passthrough lines before raising it (CORE-FIX-4d). |

These keys are also editable in Settings; a value in `.env` wins and shows
read-only there. An invalid value stops vault-core's boot. Pick a
geo-correct edge with `dig +short lancache.steamcontent.com`. New access-log
fields: `upstream_host`, `host`, `limit_conn`.

Rollout advice: keep an upstream rate cap (`VAULT_UPSTREAM_RATE`) on until
the checks in deploy/README.md "Upstream edge and connection cap" are clean
(`113` count 0, `upstream_connect_time` mostly `0.000`, at most 2x the cap
in established :80 sockets). A low rate and the cap multiply: throttled
transfers hold cap slots longer and can turn into a 503 retry loop, so
watch the 503 count when you lower the rate (open measurement
CAP-503-LOOP-1). Prefilling every installed game inside a download window
remains the best protection against MISS bursts.

Other tuning switches, one line each
([ADR-0027](../adr/0027-throughput-tuning-switches.md),
[ADR-0030](../adr/0030-aio-threads-default.md)):

- `VAULT_NGINX_AIO`: unset or `threads` = `aio threads` with `sendfile off`
  (the default); `off` = the older `sendfile on` config.
- `VAULT_NGINX_WORKERS`: `auto` or 1..16, unset = 1 worker.

## Release integrity

- **Pinned APK signing certificate (CI-SIGN-PIN-1).** The release workflow
  compares the signed APK's certificate SHA-256 with the one committed pin
  in `app/signing-cert.sha256`. **A release now fails when the APK is signed
  with a foreign key**, and a tag run fails when the pin is empty. The
  operator steps for a fork (first fill) or a deliberate key change are in
  app/README.md, paragraph "Pinned release certificate". Never change the
  pin to make a red release green: a new key breaks updates of every
  installed app.
- **Digests.** Container images are listed by `sha256:` digest (pin one with
  `image: <line>` in compose to run exactly this build); the agent files are
  covered by `SHA256SUMS`; the APK's SHA-256 and its signing certificate's
  SHA-256 are listed as well.

## Component versions

SteamHangar keeps one product version (`v0.X.Y`,
[ADR-0029](../adr/0029-version-numbering.md)), but each component carries
the version in which it last changed
([ADR-0031](../adr/0031-component-versions.md)):

**server** (vault-core, vault-api with the web UI, vault-dns, vault-proxy),
**agent** (vault-agent binaries, Scheduled Task scripts, systemd units) and
**app** (the signed Android APK). A component that did not change is reused, not rebuilt: its files and
digests come from the earlier release and are checked against it. About (web
and Android) and the "Components" section of this release show each
component's version, with "unchanged since <version>" where it was reused.
The Clients page compares agents with the agent version bundled in the
server.

## Known limitations

- **Rollback switch keeps the old problem.** `VAULT_UPSTREAM_EDGE=off`
  restores the per-name pool and with it the CGNAT port-quota exhaustion
  ([ADR-0021](../adr/0021-one-pooled-upstream-and-global-connection-cap.md)).
- **Open measurements**: D7 on `:443` (the `VAULT_TLS_CLIENT_MAX_CONNS`
  default), CAP-503-LOOP-1 (503 retry loop at low rates), HIT-PATH-1
  (server-to-client HIT throughput).
- **Not verified on real devices yet** (item 13 B): screen reader use, cover
  art on a phone, garbage collection against real chunks, multi-client
  bypass detection, the Android bottom navigation with "Desktop site" off.
- **Windows standard user**: `install-task.ps1` is tested in CI as an
  administrator only; a non-admin account is not verified (item 13 B).
- **Android app**: no "Add a device" flow (ANDROID-ADD-DEVICE-1; use the web
  UI), no tablet or foldable layout, TalkBack group semantics unverified.
- **Cover art lookups** go to Valve's store API (`api.steampowered.com`,
  no key; the tracked app ids and the server's address reach Valve), always
  on (API-FIX-5, [ADR-0026](../adr/0026-cover-refresher-stays-anonymous.md)).

## Verifying a download

- Agent files: download `SHA256SUMS` next to them and run
  `sha256sum -c --ignore-missing SHA256SUMS` (Linux) or compare
  `Get-FileHash -Algorithm SHA256 <file>` (Windows) with its line
  ([agent/README.md](../../agent/README.md)).
- APK: compare its SHA-256 with "Verify this release" (or the release it
  was reused from); `apksigner verify --print-certs <apk>` must show the
  same certificate SHA-256 digest.
- Images: pull by the listed digest.
