Question (TH-0b section 5/6, "first refinement to measure"): which nginx
connection counter should divide the aggregate — `$connections_active`
(TH-0b's Shape A, which counts idle keep-alive connections) or
`$connections_writing` (stub_status docs: connections where nginx is
writing the response back to the client)?

**Answer: `$connections_writing`.** Same result as `_active` without idle
connections (0.98x of target), and it stays at 0.98x with 8 idle
keep-alives open, where `_active` halves to 0.50x. Neither exceeded the
target.

## 2. `$connections_writing` (build E2)

`27-vault-upstream-rate.sh: upstream cap ON: 819200 bytes/s aggregate, around the clock, per-request share = total / $connections_writing (buckets 1..64, floor 12800)`

| round | wall (s) | bytes | aggregate B/s | ratio | per-request B/s | `rate=` logged |
|---|---|---|---|---|---|---|
| 1 | 1.328 | 999,232 | 752,280 | 0.918x | 758,941 | 819200 |
| 8 parallel | 9.953 | 7,993,856 | 803,125 | **0.980x** | 100,837-101,149 | 102400 (all 8) |
| 8 parallel + 8 idle keep-alive | 9.943 | 7,993,856 | 803,953 | **0.981x** | 100,901-101,075 | 102400 (all 8) |

Log excerpt (idle round, `dev.sh logs vault-core | grep 773d1005`):

```
01/Oct/2026:05:49:20 +0000 uri="/health" … cache=- rate=12800 w=0 a=8      (8th idle connection opened)
01/Oct/2026:05:49:30 +0000 uri="…773d?nocache=1" status=200 upstream_status=200 bytes_sent=999696 request_time=9.884 cache=MISS rate=102400 w=7 a=16
…                                                                                                    request_time=9.897 cache=MISS rate=102400 w=0 a=11
```

`a=16` shows the idle connections were open during the round; every
download still got total/8. Findings:

1. **Idle keep-alives are not counted** by `$connections_writing`
   (0.981x with 8 idle vs. 0.496x for `_active`).
2. **The request being rate-limited counts itself**: the single request got
   `rate=819200` (bucket 1), so the counter is >= 1 when
   `proxy_limit_rate` is evaluated at upstream-header time. The log-phase
   `w=` values (7…0) are lower because a request has already left the
   writing state when its own log line is written — they say nothing about
   the value at rate time; the `rate=` field does.
3. `/health` requests log `rate=12800` (the default bucket, `w=0` at log
   time) — irrelevant, `/health` never proxies.
4. The single request reached 0.918x (TH-0b: 0.89x), the same first-write
   granularity TH-0b section 1.1 finding 4 describes. Explanation: the
   ideal transfer time is 999,232 / 819,200 = 1.220 s, measured 1.328 s.
   The ~0.11 s difference is connect plus TTFB, which is not rate-limited
   but is included in curl's wall clock; for one request it is ~8 % of
   the run, at N=8 (a ~10 s run) about 1 %.

**Choice: `$connections_writing`** — closer to target in the idle case,
equal otherwise, never above the target in any round.

## 4. Not measured

- The window live against the operator's clock (`TZ` is TH-1b). Window
  semantics are covered offline instead: CI renders a midnight-wrapping
  window and asserts the map lines, and a loopback probe returns the
  evaluated `$vault_upstream_rate` inside (0) and outside (the cap) a
  window built around the container's current minute. A local parity run
  against `api/vault_api/schedule_window.py` (`parse_window` on a 33-value
  corpus, `contains` for 161 windows x 1440 minutes) found no mismatch
  except the documented non-ASCII-whitespace refusal.
- Slow-ramp overshoot (connections opened slower than one upstream TTFB),
  a real SteamPrefill run, HIT/MISS mixes, 30 parallel. (The logs above
  ran with 64 buckets. The shipped render has 1024, one per possible
  connection under the pinned `worker_processes 1` x
  `worker_connections 1024`, so no in-flight count reaches the default;
  `check-config-drift.sh` asserts BUCKETS >= that product.)
- `proxy_ignore_headers X-Accel-Buffering` against an upstream that sends
  the header.
